## Observations

- **g3**: no ping, no TCP — L3 unreachable. Host is either rebooting, powered
  off, or its network interface is down. Consistent with a PXE cycle.
- **g4**: pings fine (0.28 ms latency), TCP port 22 accepts connections.
  sshd's banner line is `Not allowed at this time`. Later probes get
  `kex_exchange_identification: read: Connection reset by peer`. The banner
  message is produced by `pam_time.so` / `pam_access.so` when a user is
  outside an allowed login window, OR by explicit `AllowUsers` /
  `DenyUsers` with a time-of-day gate.

## Leading hypothesis

A daily maintenance window covering ~03:00-??? CDT is active on both
hosts. g3 is in the "hard reboot" part of that window (PXE re-image);
g4 has already booted but its sshd is gated by PAM while the maintenance
is ongoing. This matches the user's earlier note that "g3/g4 可能以每天
一次的频率 pxe reboot".

Secondary hypothesis (weaker): the 4-proc fork-mode bench I ran on g4 put
the kernel into a bad state that took out sshd. Weak because (a) the
banner message is specifically from PAM, not a crashed daemon; (b) the
bench was Option C which has no replicator thread and no cross-host ring
writes — it's a read-modify-write in a single bucket table — it's hard
to see how it would wedge the kernel; (c) g3 went down FIRST, before any
diagnostic I ran on g4.

If Hypothesis 1 holds, g3/g4 should return when the maintenance window
closes. No user intervention needed.

## What would confirm / refute each hypothesis

- **Hypothesis 1 (scheduled maintenance)**:
  - After the window closes (probably within ~1 h), both slaves come back
    cleanly.
  - Next day: observe whether a similar outage window happens at
    approximately the same wall-clock time.
  - `crontab -l` on g3/g4 once they are back should show a maintenance
    job. `/etc/security/access.conf` or `/etc/security/time.conf` should
    show the login gate.
  - `last reboot` / `journalctl -b -1` after reboot should show whether
    g3 had a clean reboot (PXE) vs a kernel panic.

- **Hypothesis 2 (bench wedge)**:
  - After g4 recovers, try to run the 4-proc fork-mode bench again. If it
    reliably wedges and leaves sshd unreachable afterwards, this hypothesis
    is plausible.
  - Look for an OOM killer message in `dmesg` right before sshd stopped
    responding.

## What we learned independent of the outage

- LFM mutex (Lamport's Fast Mutex) *does* deadlock at `num_hosts >= 3`
  on the g3/g4 PCIe-switched CXL memory server, independent of whether
  the host then loses sshd. 2-proc contention works cleanly at ~17 μs
  per critical section. This finding is documented in
  `docs/g34_bench/g34_lfm_finding.md` and is the workaround for the
  9 AM deliverable (`FUSEE_NUM_HOSTS=2` instead of 4).
- Cross-host byte-level sharing via the PCIe switch *does* work
  (`cxl_xhost_test` passed on g3 ↔ g4 at 02:56).
