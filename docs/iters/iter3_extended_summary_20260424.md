upstream LFM, compiled only into `fusee_cxl_decomp` when

## 3. Multi-flusher bug — **PLANNED, TESTED, CAUSE FOUND, FIX FAILED → REVERTED**

- Attempt commits: `94da706` (scaffold) → `aeadca9` (ready-flag
  hardening).
- Revert commit: `5189086`.

### Symptoms

- V1 (`94da706`) hung at T ≥ 32 when `FUSEE_BATCH_NUM_FLUSHERS ≥ 2`.
- V2 (`aeadca9`) hung even at T=1 N=1 under contention.

### Causes identified

**Bug 1 (V1 — producer/consumer cursor race):**
`MicroBatchRing::append` publishes to the dirty queue via
`dq_tail.fetch_add(1)` and leaves the slot writable unconditionally.
Consumer advances `dq_head` with plain `++`. On queue overflow the
producer **rolls back `queued` to 0** but **does not roll back the
tail advance**. The consumer subsequently dequeues an unwritten
slot (reads stale `0`), the producer's `queued=0` rollback means
the next writer cannot re-enqueue, and the bucket freezes. At T ≥
32 this fires reliably enough to deadlock within seconds.

**Bug 2 (V2 — ready-flag without matched consumer spin):**
The V2 ready-flag hardening intended to let the consumer spin on
`ready==1` before reading the slot. On overflow, V2 still skips
the slot+ready-flag write (correctly) but the consumer spins on
`ready==0` forever because V1's dequeue-then-rollback path kept
raising `dq_tail` past writes the producer never published. The
ready-flag alone did not fix V1's tail vs queued-flag inconsistency.

### Correct design (for a future attempt)

- Producer claim must be **all-or-nothing**: either both
  `dq_tail.fetch_add` and the slot+ready write happen, or neither.
  Easiest form is a CAS loop that claims the tail only after it
  has confirmed `tail - head < CAP` and published the slot.
- Consumer must spin on the ready flag before reading the slot,
  and must clear `queued` only **after** it has drained the
  bucket's ring segment.
- Multi-flusher partitioning is safe under `bucket_idx % N` only
  if each flusher owns a disjoint bucket subset for the duration
  of a drain cycle; `queued` must be per-(bucket, flusher) or the
  dirty queue must be one per flusher.

### Current production state

- Branch `feat/cxl-migration` at commit `5189086` (reverted to the
  `072070c` semantics: N=1 flusher, no ready flag).
- `FUSEE_BATCH_NUM_FLUSHERS` env variable is removed; production
  path is single-flusher.
- V1/V2 commits stay in history for the future attempt.

### Why the fix was abandoned in this window

After the revert, even the known-good `072070c` binary intermittently
hung at T=86 on the slave hosts. Hypothesis: leftover devdax /
SysV-like state after many killed processes during V2 debugging.
Rebooting the slaves clears it but was out of scope for the 11AM
time budget. This is a tail-risk note, not a code regression.
